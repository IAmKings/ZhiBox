# W1 性能实测发现：长度×延迟矩阵 + GPU 路线

- **日期**：2026-10-15（三档全部完成）
- **工具**：`LengthLatencyBenchmark`（app 内"长度×GPU"入口 / `scripts/run_latency_matrix.sh`）

## 发现 1（最重要）：运行时输入上限是 1024 token，不是 8192

litertlm 0.18.0 的 .litertlm 编译签名限制输入序列 ≤1024 token（模型卡的 8192 上下文不适用于此构建）。实测一次确定性失败：800 字中文 → **1080 token > 1024**（INVALID_ARGUMENT，`embedding_engine_impl.cc:1598`）。

- **中文密度校准**：≈1.35 token/字（800 字 → 1080 token 精确吻合）；
- **边界区不稳定**：700–800 字在后续复测中又可通过——上限判定存在不一致性（可能与内部批处理/填充有关），**700–800 字视为红线区，不可依赖**；
- **产品修复（已落地）**：Chunker 默认 `maxChars` 800→600（600 字 × 1.35 + 任务前缀 ≈ 830 token，安全余量）；`estimateTokens` CJK 系数 1→1.4→1.35 校准（曾按 1 计算会系统性低估 35%）；
- **W1 验收为何没踩雷**：语料块平均 ~680 字但分布偏短，恰好无一越界——纯运气，此修复消除了地雷；
- **上游跟踪**：加入 UPSTREAM_WATCH W2/W3 项——litertlm 新版若放宽签名长度（或暴露 maxInputLength 生效配置）需重测。

## 发现 2：CPU 延迟随长度的真实曲线（三档，p50）

| 输入 | ≈token | 旗舰 8 Elite | K60U 天玑9200+ | K40 天玑1200 |
|---|---|---|---|---|
| 30 字 | 41 | 62ms | 97ms | 126ms |
| 200 字 | 250 | 131ms | 218ms | 327ms |
| 400 字 | 439 | 132ms | 217ms | 349ms |
| **600 字（默认块）** | 683 | **346ms** | **553ms** | **1026ms** |
| 700 字 | 743 | 384ms | 546ms | 1099ms |
| 800 字（红线区） | 878 | 390ms | 582ms | 1121ms |

曲线形态三档一致：200–400 字平台期 + 600 字附近跳变（疑似内核路径切换）；三档算力比 ≈ 1 : 1.6 : 3。**真实 chunk 的单条嵌入是亚秒到 1 秒级（按档位 0.35/0.55/1.03s），不是短句基准暗示的 60-145ms**。

## 发现 3：导入开销归因修正（推翻此前结论）

以真实块尺寸计，**嵌入计算占导入耗时 60–90%**，此前"80% 管线开销"的归因错误（短句基准误外推）。优化优先级：等 ML Kit/NPU ≫ 管线微优化（去抖等仍值得但收益上限小）。

## 发现 4：GPU 路线最终判定——仅旗舰可用，产品价值倒挂

| 档位 | SoC/GPU | GPU 可用 | 600 字提速 |
|---|---|---|---|
| 高端 | SM8750 / Adreno | ✅ | 346→143ms（**2.4×**，且随长度增大到 2.7×） |
| 中端 | MT6985 / 天玑9200+ | ❌ 引擎创建失败 | — |
| 低端 | MT6893 / 天玑1200 | ❌ 引擎创建失败 | — |

R4 完全坐实：OpenCL 路径只在 Qualcomm 旗舰工作。**决定性的是价值倒挂——GPU 加速恰好在最不需要它的设备（CPU 本就最快）上可用，而最需要加速的两档 MediaTek 不可用。** 产品结论：CPU 为全档默认；GPU 不做通用优化路线（最多作为旗舰的能力检测型可选项，优先级低）；导入性能的正解仍是 ML Kit/NPU（W1 监控项）。

## 对 W2/W3 的输入

1. 检索侧无关（查询是短文本，62-126ms 级）——导入吞吐是唯一受影响链路；
2. 大文档导入预期（600 字块）：低端机 ≈ 1s/块、中端 0.55s、旗舰 0.35s——MVP 可接受，写入产品文档；
3. ML Kit（W1 监控）价值权重再上调：同时解决延迟（NPU ~10×）、内存（0.5GB）、1024 上限（托管分词）三个问题，且是 GPU 路线倒挂后的唯一加速出路；
4. GPU 不可用设备占三档之二——任何依赖 GPU 的设计直接排除。

## 附：导入管线优化①②实测（2026-10-15，K40 同语料对照）

| 指标 | 基线（800字块+链式worker+无去抖） | 优化后（600字块+批量worker+300ms去抖） |
|---|---|---|
| 总时长 | 210s | **198s** |
| chunks | 298 | 380（+27%，块上限 800→600 所致） |
| 单块吞吐 | 1.42 块/s | **1.92 块/s（+35%）** |
| 结果 | 100/100 done | 100/100 done |

块数多 27% 而总时长反降——开销削减（状态导出去抖 + 批量 worker 摊薄）被实证吸收。优化③（嵌入/写库流水线化）按修正归因放弃；优化④（前台服务）留 W3 且优先级上调（导入实测比预估更慢，后台冻结窗口更长）。
