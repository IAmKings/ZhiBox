# W1 性能实测发现：长度×延迟矩阵 + GPU 路线（进行中）

- **日期**：2026-10-15
- **工具**：`LengthLatencyBenchmark`（app 内"长度×GPU"入口 / `scripts/run_latency_matrix.sh`）
- **状态**：低端档（K40）CPU/GPU 已测；旗舰与 K60 Ultra 待接入后跑同一脚本补齐

## 发现 1（最重要）：运行时输入上限是 1024 token，不是 8192

litertlm 0.18.0 的 .litertlm 编译签名限制输入序列 ≤1024 token（模型卡的 8192 上下文不适用于此构建）。实测一次确定性失败：800 字中文 → **1080 token > 1024**（INVALID_ARGUMENT，`embedding_engine_impl.cc:1598`）。

- **中文密度校准**：≈1.35 token/字（800 字 → 1080 token 精确吻合）；
- **边界区不稳定**：700–800 字在后续复测中又可通过——上限判定存在不一致性（可能与内部批处理/填充有关），**700–800 字视为红线区，不可依赖**；
- **产品修复（已落地）**：Chunker 默认 `maxChars` 800→600（600 字 × 1.35 + 任务前缀 ≈ 830 token，安全余量）；`estimateTokens` CJK 系数 1→1.4→1.35 校准（曾按 1 计算会系统性低估 35%）；
- **W1 验收为何没踩雷**：语料块平均 ~680 字但分布偏短，恰好无一越界——纯运气，此修复消除了地雷；
- **上游跟踪**：加入 UPSTREAM_WATCH W2/W3 项——litertlm 新版若放宽签名长度（或暴露 maxInputLength 生效配置）需重测。

## 发现 2：CPU 延迟随长度的真实曲线（K40 · 天玑 1200 · CPU/XNNPack）

| 输入 | ≈token | p50 | p95 |
|---|---|---|---|
| 30 字 | 41 | 126ms | 129ms |
| 200 字 | 250 | 327ms | 337ms |
| 400 字 | 439 | 349ms | 354ms |
| **600 字（新默认）** | 683 | **1026ms** | 1094ms |
| 700 字 | 743 | 1099ms | 1129ms |
| 800 字（红线区） | 878 | 1121ms | 1193ms |

曲线特征：200→400 字近乎平台（327→349ms），400→600 字跳变 3 倍（疑似内部内核路径切换）——**真实 chunk 的单条嵌入在低端机上是亚秒到 1 秒级，不是 P0-2 短句基准暗示的 145ms**。

## 发现 3：导入开销归因修正（推翻此前结论）

以真实块尺寸（数百字）计，**嵌入计算占导入耗时 60–90%，此前"80% 管线开销"的归因错误**（那是把 30 字基准外推到全部块的结果）。导入优化方向相应修正：削减每块嵌入延迟（等 ML Kit/NPU）≫ 管线微优化（状态去抖等仍值得做但收益上限小）。

## 发现 4：GPU 路线在低端档不可用

K40（天玑 1200）：GPU delegate **引擎创建即失败**（`embedding_engine_impl.cc:520`，UNKNOWN）——OpenCL 路径在该 SoC/运行时组合上不可用。R4（GPU 脆弱性）在低端档坐实；GPU 路线最多作为中高端机型的可选加速，永远不能做默认。旗舰/K60 Ultra 的 GPU 实测待设备接入。

## 对 W2/W3 的输入

1. 检索侧无关（查询是短文本，126ms 级）——导入吞吐是唯一受影响链路；
2. 大文档导入预期：千字文档 ≈ 2 块 × 1s ≈ 2s/文档（低端机）——MVP 可接受，文档化即可；
3. ML Kit（W1 监控）的价值权重再上调：同时解决延迟（NPU ~10×）与内存（0.5GB）与上限（托管分词）三个问题。
