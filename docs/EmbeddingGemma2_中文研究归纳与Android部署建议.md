# EmbeddingGemma 2：中文研究归纳与 Android 端侧部署建议

> **原文**：[Bring multimodal semantic search to the edge with EmbeddingGemma 2](https://developers.googleblog.com/google-ai-edge-with-embeddinggemma-2/)  
> **发布方**：Google Developers Blog（Google AI Edge Team、Android ML Team）  
> **文章日期**：2026-10-06  
> **整理目的**：提炼文章核心信息，并转化为可执行的 Android 端侧 AI 技术选型与优化建议。

---

## 1. 执行摘要

EmbeddingGemma 2 是一个约 **740M 参数的开放权重多模态 Embedding 模型**。它可以把文本、图像、视频帧和音频映射到统一的向量空间，主要用于语义搜索、跨模态检索、分类和低延迟决策，而不是像生成式 LLM 那样直接生成长文本。

文章最值得借鉴的工程思路：

1. **让专用 Embedding 模型承担检索和匹配任务**，不要把所有简单任务都交给大语言模型。
2. **按需加载模态编码器**，避免在不需要图像或音频功能时加载完整多模态模型。
3. **将模型推理和向量检索分开优化**：模型负责生成向量，检索器负责从索引中找出候选结果。
4. **把向量维度、量化和索引结构纳入整体优化**，而不只是压缩模型文件。
5. **不要将“框架支持 NPU”理解成“模型必然在 NPU 上运行”**；必须在目标设备上验证实际执行后端、延迟、内存与检索质量。

对于 Android 项目，建议先建立可靠的 CPU 基线，验证检索质量与端到端体验，再评估 MediaPipe Tasks、ML Kit 和 LiteRT 的适配情况及硬件加速收益。

## 2. EmbeddingGemma 2 是什么？

### 2.1 与生成式 LLM 的区别

| 类型 | 核心职责 | 常见输出 | 典型用途 |
|---|---|---|---|
| 生成式 LLM | 根据上下文生成内容 | 文本或其他生成结果 | 问答、总结、写作、复杂推理 |
| Embedding 模型 | 将内容映射到向量空间 | 数值向量 | 语义搜索、相似度匹配、分类、检索 |
| 向量检索系统 | 从向量索引中查找近似匹配项 | 排序后的候选结果 | 图片搜索、文档检索、知识库召回 |

EmbeddingGemma 2 的重点是把不同模态内容转换为可比较的向量，便于在本地进行检索和匹配。检索本身通常不需要调用生成式 LLM；只有需要根据检索结果生成自然语言答案时，才有必要增加 LLM。

### 2.2 文章介绍的能力

| 项目 | 文章信息 | 解读与注意事项 |
|---|---|---|
| 模型规模 | 约 740M 参数 | 参数量不等于模型文件大小，也不等于运行时 RAM |
| 模态 | 文本、图像、视频帧、音频 | 统一向量空间有助于跨模态检索 |
| 默认向量维度 | 768 维 | 具体 API、模型变体应以模型卡为准 |
| 可截断维度 | 128～512 维 | 可用 MRL 降低向量存储和索引成本，但要验证检索质量 |
| 量化 | 文章提到 INT4、INT8 量化感知训练（QAT） | 具体量化模型、后端支持及精度损失需要实测 |
| 端侧内存示例 | Pixel 11 Pro 上，文本权重活动 RAM 约 191 MB；完整多模态模型约 567 MB | 这是文章报告的特定设备与配置结果，不代表所有手机的固定内存需求 |
| 主要用途 | 本地语义搜索、媒体检索、分类和决策 | 可离线运行，适合隐私敏感场景 |

来源：[Google Developers Blog 原文](https://developers.googleblog.com/google-ai-edge-with-embeddinggemma-2/)。具体文件大小、API、量化版本与兼容设备应以[模型卡](https://huggingface.co/)及官方开发文档为准。

## 3. 文章展示的应用场景

### 3.1 Instant Media Search：本地图片与媒体搜索

核心流程：

1. 把用户输入的自然语言查询转换为向量。
2. 为本地图片或媒体生成向量。
3. 将媒体向量存入本地 SQLite 数据库。
4. 根据余弦相似度等方法对候选内容排序。
5. 用户输入变化时，动态刷新搜索结果。

示例查询：“找出猫趴在键盘上睡觉的照片”。

这类方案不必先为每张图片生成文字描述，再用传统关键词搜索；可以直接对查询文本和媒体的向量进行匹配。文章还展示了使用一张示例图片查找视觉或语义相似图片的能力。

### 3.2 Video Moments Finder：视频片段检索

文章展示的方案会为本地视频中的视觉关键帧和音频片段建立向量索引。用户输入“孩子在笑”“狗接住飞盘”等描述后，系统检索匹配片段并返回相应时间戳。

**工程含义：** 可以减少“先做语音转文字、再为视频生成文本描述、最后搜索文本”的串联步骤。但具体应用仍需设计视频抽帧策略、音频分段策略、索引更新和时间戳映射。

### 3.3 AI Edge Foresight：本地会议与个人知识检索

文章介绍了面向 Mac 的实验性应用，组合 EmbeddingGemma 2 和 Gemma 4，用于本地会议记录、笔记补充、对话上下文检索，以及对文档、转录内容和笔记的自然语言搜索。

其架构思路是：

- Embedding 模型：定位相关信息。
- 本地索引：管理个人资料并提供检索。
- 生成式模型：在需要时整理信息、回答问题或补充笔记。

这些组件各司其职，避免用一个大模型处理所有环节。

## 4. 关键技术设计及其价值

### 4.1 模块化编码器：按需加载

文章强调可以按任务加载需要的模态编码器，例如：

- 文本搜索：仅使用文本相关模块。
- 图片或视频搜索：使用文本与视觉模块。
- 语音备忘录搜索：在需要时启用音频模块。

**建议：** 不要默认在 App 启动时加载完整多模态模型。应根据产品功能、设备内存和用户当前任务选择必要模块，并验证实际运行时是否支持这种粒度的加载与释放。

### 4.2 INT4 / INT8 量化感知训练

QAT（Quantization-Aware Training）在训练过程中考虑低精度量化的影响。文章提到 INT4 和 INT8 量化，目标是降低模型的存储与运行成本。

量化评估不能只看模型大小和推理速度，还要评估检索质量，例如：

- Recall@K 或 Top-K 命中率；
- 排序质量；
- 跨语言查询表现；
- 相似图片、商品或文档的区分能力。

不能假定 INT4 一定比 INT8 快：最终性能取决于设备硬件、算子实现、后端支持、数据转换开销和模型配置。

### 4.3 动态计算图与视觉 Token 预算

文章提到根据输入大小选择合适的计算图，并允许控制视觉 Token 预算。其价值在于减少不必要的计算，但预算越低也可能损失图像细节。

**建议：** 为常见输入设定合理预算，通过真实数据集和目标设备测试，寻找延迟、内存与检索准确率之间的平衡。

### 4.4 MRL：截断向量维度以节省存储

Matryoshka Representation Learning（MRL）支持在输出阶段截断向量维度。文章介绍默认 768 维，并支持截断至 128～512 维；文中称这种方式可将本地存储和索引占用最多降低约 8 倍。

#### 理论存储估算

假设每个维度使用 FP32（4 字节），不计索引、数据库和元数据：

| 向量维度 | 每条向量大小 | 100,000 条向量的纯向量数据 |
|---:|---:|---:|
| 768 | 3,072 字节 | 约 293 MiB |
| 512 | 2,048 字节 | 约 195 MiB |
| 256 | 1,024 字节 | 约 97.7 MiB |
| 128 | 512 字节 | 约 48.8 MiB |

这是理论值，不包含 ANN 索引、SQLite 开销、元数据和缓存。768 维截断到 128 维，纯向量数据减少 6 倍；实际总存储缩减比例会因索引结构而不同。

**建议：** 至少比较 128、256、512 和 768 维的检索质量与延迟，再决定生产配置。维度相同并不意味着不同 Embedding 模型的向量空间兼容；更换模型时通常需要重新生成索引。

## 5. 文章公布的视觉 Embedding 性能数据

文章中的测试表描述的是**单张图片的视觉 Embedding 延迟**，每张图片的视觉 Token 预算上限为 70。它不是完整相册搜索或视频检索的端到端延迟。

| 平台 | 设备 | 加速器 | 单张图片延迟 | 对应吞吐量 |
|---|---|---|---:|---:|
| 移动端 | iPhone 18 Pro | CPU | 191 ms | 约 5.2 张/秒 |
| 移动端 | iPhone 18 Pro | GPU | 69.8 ms | 约 14.3 张/秒 |
| 移动端 | Pixel 11 Pro XL | NPU | 48.9 ms | 约 20.6 张/秒 |
| 桌面端 | MacBook M5 Pro | CPU | 151 ms | 约 6.6 张/秒 |
| 桌面端 | MacBook M5 Pro | GPU | 37.3 ms | 约 26.9 张/秒 |
| 桌面端 | Dell XPS 16 | NPU | 49.8 ms | 约 20.1 张/秒 |
| IoT | Raspberry Pi 5 | CPU | 1,761 ms | 约 0.6 张/秒 |
| IoT | NVIDIA Jetson Nano | GPU | 485 ms | 约 2.1 张/秒 |
| IoT | Arduino Ventuno Q | NPU | 135 ms | 约 7.4 张/秒 |

来源：Google Developers Blog 中的性能表及配套图片：[原文](https://developers.googleblog.com/google-ai-edge-with-embeddinggemma-2/)。

### 如何正确解读

1. **加速器会显著影响结果，但不能跨设备简单比较。** 不同设备、芯片、驱动、模型编译方式和精度配置都会影响延迟。
2. **NPU 值得测试，但不是自动保证。** 只有模型、算子、量化方式和运行时都兼容时，才能获得预期收益。
3. **单张视觉 Embedding 延迟不等于端到端搜索延迟。** 完整流程还包括图片解码、预处理、推理、向量存储、ANN 检索、排序和 UI 更新。
4. **批量索引和交互式搜索的目标不同。** 批量索引关注吞吐量、温度和功耗；交互式搜索更关注首个结果延迟和输入响应。

## 6. Google 提供的开发路线

### 6.1 ML Kit：Android 产品化路线

文章称 Google 计划在发布后的数周内通过 ML Kit 提供 EmbeddingGemma 2 的 Android 集成，并提及 NPU 加速（设备支持时）和自动模型更新。

**重要状态说明：** 这属于原文发布时的路线图表述，不能仅凭文章断定当前所有设备、所有版本均已可用。实施前应核对 ML Kit 当前文档、API 状态、最低系统要求、设备兼容范围和模型分发方式。

适合：
- 希望尽快集成到正式 Android 应用；
- 希望减少模型生命周期、分发和 APK 体积管理工作；
- 接受平台提供的抽象层和能力边界。

### 6.2 MediaPipe Tasks：跨平台快速开发

文章介绍的组件：

| 组件 | 作用 | 使用场景 |
|---|---|---|
| Universal Embedder | 处理输入预处理并生成向量 | 将文本或图像转换为 Embedding |
| Semantic Retriever | 管理向量索引并进行近似最近邻搜索（ANN） | 本地图片、文档和媒体检索 |
| Decision Task | 根据 Embedding 进行候选匹配和决策 | 分类、意图路由、动作预测 |

文章表示 Universal Embedder 可以处理图像缩放、张量归一化和多模态 Token 化，输出 768 维或截断后的 128～512 维向量。Semantic Retriever 的 ANN 检索可达到个位数毫秒级；这是检索组件的描述，不代表模型推理或端到端搜索也只有个位数毫秒。

适合：
- 先验证产品原型；
- 希望复用检索组件；
- 需要覆盖 Android、iOS、桌面或 Web；
- 不想从零实现所有预处理与向量检索逻辑。

### 6.3 LiteRT：更细粒度控制推理与加速

文章将 LiteRT 定位为需要精细控制处理流程和加速时的路线，并介绍了 CPU、GPU、NPU 的统一加速能力，以及 `.litertlm` 模型包在支持平台上的 CPU/GPU 执行方式。

适合：
- 需要分析实际执行后端；
- 需要控制模型输入、量化和运行时配置；
- 希望针对特定 SoC 做性能优化；
- 希望比较 CPU、GPU 和 NPU 的实际效果。

**关键提醒：** 模型文件可以加载，不代表 NPU 一定可用。应检查算子覆盖、模型编译/量化要求、后端初始化结果、算子回退和数据传输开销。

### 6.4 技术路线选择表

| 目标 | 建议优先评估 | 原因 |
|---|---|---|
| 快速体验和验证场景 | Google AI Edge Gallery | 先确认用户体验和模型能力 |
| 跨平台检索原型 | MediaPipe Tasks | 抽象预处理、Embedding 与检索流程 |
| 正式 Android 产品 | 核实 ML Kit 当前支持情况 | 关注产品化 API、分发和生命周期管理 |
| 研究 NPU 与性能 | LiteRT + 目标设备实测 | 更适合深入分析执行后端和性能瓶颈 |
| 自定义推理管线 | LiteRT 及相关开发工具 | 更适合需要细粒度控制的场景 |

这些路线并非完全互斥。可以先用 MediaPipe Tasks 验证功能，再根据性能和可控性需求决定是否下沉到 LiteRT。

## 7. 推荐的 Android 本地语义搜索架构

### 7.1 纯搜索流程

```text
用户查询
   │
   ▼
Embedding 模型
   │
   ▼
查询向量
   │
   ▼
本地向量检索 / ANN
   │
   ▼
Top-K 候选
   │
   ▼
可选：二次排序与过滤
   │
   ▼
展示结果
```

如果需求只是搜索和匹配，不必在每次请求中调用生成式 LLM。

### 7.2 带本地问答的 RAG 流程

```text
用户问题
   │
   ▼
Embedding 检索
   │
   ▼
相关文档片段 / 本地内容
   │
   ▼
本地 LLM（按需调用）
   │
   ▼
自然语言答案
```

这种拆分允许独立优化检索和生成模块。更换 Embedding 模型时，要验证旧索引是否仍然兼容；通常需要重新生成向量。

### 7.3 推荐的数据处理流程

1. 选择需要索引的媒体或文档。
2. 进行必要的解码、抽帧或分段。
3. 使用 Embedding 模型生成向量。
4. 将向量、内容 ID、时间戳和元数据持久化。
5. 新内容到来时增量更新索引。
6. 查询时生成查询向量并检索 Top-K。
7. 根据需要进行过滤、重排或调用 LLM。
8. 记录质量、延迟、内存和功耗指标。

## 8. 性能评估与验收建议

不要只比较“ONNX、LiteRT 或 GGUF 谁更快”，也不要只测模型文件大小。应在同一设备、同一数据集、相近精度和相同输入条件下比较完整方案。

### 8.1 必测指标

| 指标 | 测量目的 |
|---|---|
| 模型加载时间 | 评估冷启动体验 |
| 首次调用延迟 | 捕捉首次编译、初始化和缓存影响 |
| 稳态 Embedding 延迟 | 评估交互式查询速度 |
| 批量处理吞吐量 | 评估建立索引的效率 |
| 端到端搜索延迟 | 衡量用户实际感知的速度 |
| 峰值 RAM | 确认低内存设备是否稳定 |
| 持久化存储占用 | 评估模型、向量和索引成本 |
| CPU/GPU/NPU 执行情况 | 验证是否真正使用目标加速器 |
| 温度与持续性能 | 检查热降频和长期运行表现 |
| 检索质量 | 防止量化或降维造成搜索质量下降 |

### 8.2 建议的实验矩阵

- **向量维度：** 128、256、512、768。
- **量化配置：** 按实际可用模型比较 INT4、INT8 及其他官方支持精度。
- **执行后端：** CPU、GPU、NPU（仅在目标设备与模型支持时）。
- **数据规模：** 小、中、大规模索引，覆盖真实预期使用量。
- **查询类型：** 短文本、长文本、多语言、模糊描述、图像到图像、文本到图像。
- **运行状态：** 冷启动、热启动、连续批处理、长时间运行。
- **质量指标：** Recall@K、Top-K 命中率、排序指标及人工抽检。

### 8.3 建议的验收原则

- 先定义产品体验目标，再设定延迟和内存门槛。
- 对比不同配置时保持数据集、查询和测试环境一致。
- 记录设备型号、系统版本、运行时版本、模型文件、量化配置和后端。
- 将检索质量作为硬指标，不允许只以速度提升作为成功标准。
- 至少在目标设备范围内的代表性机型测试，不以单台旗舰机推断整个 Android 生态。

## 9. 面向项目落地的优先级建议

### 第一阶段：验证业务价值

- 使用 AI Edge Gallery 体验图片和视频语义搜索。
- 选取真实业务数据集，验证查询是否能找到正确内容。
- 确认是否确实需要多模态检索，还是文本 Embedding 已足够。

### 第二阶段：建立 CPU 基线

- 使用可用的官方模型与框架搭建最小端到端原型。
- 记录加载时间、Embedding 延迟、检索延迟、峰值 RAM 和检索质量。
- 先确保在没有 NPU 的设备上也能正确工作。

### 第三阶段：优化向量和索引

- 比较不同向量维度。
- 比较直接相似度计算与 ANN 检索。
- 实现增量索引和索引版本管理。
- 评估量化对召回率与排序的影响。

### 第四阶段：评估硬件加速

- 核实 ML Kit、MediaPipe Tasks 或 LiteRT 对目标设备的实际支持。
- 分别测量 CPU、GPU 和 NPU 路径。
- 确认是否发生算子回退，并比较端到端延迟。
- 保留可靠的 CPU 降级路径。

### 第五阶段：按需引入 LLM

只有在业务需要生成摘要、自然语言回答或复杂推理时，才增加本地 LLM。Embedding 检索与 LLM 生成应分开测量、分别优化。

## 10. 主要风险与容易误判的地方

1. **把模型参数量当成 RAM 需求。** 运行时还包含激活张量、缓存、索引和应用本身的内存。
2. **把 NPU 支持当成自动加速。** 模型、算子、量化、编译器和后端必须匹配。
3. **把模型推理延迟当成搜索延迟。** 完整链路还包含预处理、索引、检索与 UI。
4. **盲目降低向量维度。** 需要在真实数据集上测量检索质量。
5. **随意替换 Embedding 模型。** 不同模型的向量空间通常不兼容，可能需要重建索引。
6. **忽略索引与元数据的存储成本。** 大规模媒体检索中，索引成本可能不可忽视。
7. **把文章中的路线图当成当前既成事实。** ML Kit 的可用性、API、设备覆盖和 NPU 支持应以当前官方文档为准。
8. **将不同设备的性能数字直接横向推断。** 硬件、软件栈、输入和测试条件可能不同。

## 12. 最终结论

EmbeddingGemma 2 的价值不只是提供一个新的多模态模型，而是展示了一种更适合端侧 AI 的系统设计：**专用 Embedding 模型负责检索和匹配，向量检索组件负责查找候选内容，生成式 LLM 只在需要生成或推理时参与。**

对于 Android 开发，推荐的策略是：

1. 先用 EmbeddingGemma 2 验证语义搜索是否满足业务需求。
2. 通过 MediaPipe Tasks 快速搭建可运行的端到端原型。
3. 将向量维度、量化、索引和增量更新纳入整体优化。
4. 以 CPU 作为可靠基线，再在目标设备上验证 GPU/NPU。
5. 用真实数据集和真实设备评估端到端延迟、RAM、功耗与检索质量。

相比一开始就追求某个推理框架或 NPU 的理论峰值，这种从业务质量、完整链路和设备兼容性出发的路线，更有利于做出稳定、可维护的 Android 端侧 AI 产品。
