# 应用内更新人工验收手册（内测发布）

> 适用：准备内测 Release、需要人工验证「普通更新 / 灰度 / 强制 / Beta / 网络降级」。
> 先读 `docs/product/APP_UPDATE_SPEC.md` 了解契约；本手册只讲怎么测、怎么记录、怎么放行。
> 当前基线：**v0.1.11（latest）**；可用历史版本：v0.1.6 ~ v0.1.11。

## 0. 结论先行（内测放行必须满足）

1. **普通更新全链路**（检查→弹窗→下载→校验→安装→版本正确）在至少 2 台真机、2 种网络通过；
2. **灰度 0% 不弹窗 / 100% 弹窗** 两个边界必须确定通过（中间比例仅抽样记录）；
3. **强制更新** 在可清空设备上验证：不可取消、安装后解除、连续失败 3 次可暂时退出；
4. **Beta 通道**：stable 看不到 prerelease，开启 Beta 后可见；
5. 受限网络下 **APK 与 `update.json` 都能镜像回退**（灰度/强制仍生效）；
6. 以上用例 0 P0 缺陷；已知限制写入发布说明。

## 1. 测试环境

### 1.1 设备（建议 ≥3 台）

| 设备 | 用途 | 要求 |
|---|---|---|
| A：正常网络（Wi‑Fi 可直连 GitHub） | 普通更新、前后台、安装器 | Android 13+，可清空数据 |
| B：受限网络（国内移动网络，直连 GitHub 资产超时） | 镜像回退、灰度/强制元数据回退 | 与 A 不同厂商/系统更好 |
| C：可清空备用机 | 强制更新、失败逃生、降级 | 允许卸载/清数据 |

另建议覆盖：Android 12/13/14/15+、MIUI/ColorOS/原生 至少各一台厂商安装器（未知来源/风险确认流程不同）。

### 1.2 工具与记录

- `adb`（安装、截图、logcat、`dumpsys`）；
- GitHub Release 页面（公开仓库无需登录）；`gh` CLI 可选；
- 每台设备记录：型号、系统版本、网络、起始版本、目标版本、APK SHA-256、时间；
- 证据：截图/录屏；异常时 `adb logcat -d | grep AppUpdate`、`adb shell dumpsys notification --noredact`、`adb shell dumpsys package com.zhibox.memory`。

### 1.3 安装历史版本

1. 打开 https://github.com/IAmKings/ZhiBox/releases 对应 tag；
2. 下载 `zhibox-<ver>-<sha7>-release-signed.apk`，用同名 `.sha256` 校验；
3. `adb install -r <apk>` 或文件管理器安装；
4. **降级必须卸载重装**（versionCode 降低会被系统拒绝）；卸载会清空本地资料。

### 1.4 版本能力矩阵（重要）

| 起始版本 | 更新能力 | 灰度/强制支持 | 建议用途 |
|---|---|---|---|
| v0.1.6 | 进程内下载、弹窗、SHA/签名校验、镜像回退；无后台/通知 | ❌ 不识别 `update.json` | 只验证「旧客户端普通升级」 |
| v0.1.7 | 后台下载/通知/跨进程续传、设置搜索、自动检查开关、Beta | ⚠️ 有解析但**不跟随 GitHub 资产 302**，元数据实际被忽略 | 旧客户端普通升级、后台链路 |
| v0.1.8 | 跨线路续传修复 | ⚠️ 同上 | 旧客户端普通升级 |
| v0.1.9 | 元数据重定向修复、通知被拒回前台续装 | ⚠️ 元数据直连 CDN 不可达时回退默认（无镜像） | 普通更新、通知降级 |
| v0.1.10 | `update.json` cache-buster | ⚠️ 元数据仍无镜像回退 | 普通更新、灰度（网络可达时） |
| **v0.1.11** | 元数据镜像回退 | ✅ **推荐作为灰度/强制测试基线** | 全部场景 |

> 结论：**灰度/强制一定要用 v0.1.11 作为起始客户端**；历史版本只用于验证普通升级兼容性。

## 2. 发布物准备（测试前由发布负责人完成）

### 2.1 内测目标版本

- 用正式 `.github/workflows/release.yml` 构建：tag 与 `versionName` 一致，release keystore 与历史版本一致（可覆盖升级）；
- 内测建议发 **prerelease**（如 `v0.1.12-beta.1`），避免影响 stable 用户；
- 产物必须包含：APK、`.sha256`、mapping、`update.json`。

### 2.2 三种场景的发布隔离（推荐）

| 场景 | 发布物 | `release/update-policy.json` |
|---|---|---|
| 普通更新（内测 Beta） | `v0.1.12-beta.1`（prerelease） | `rolloutPercent=100`、`minSupportedVersion=0.1.0` |
| 灰度边界 | 临时 prerelease（如 `v0.1.12-qa.1`） | `rolloutPercent=0`（随后另发一个 100 的 drill） |
| 强制更新 | 临时 prerelease（如 `v0.1.12-force.1`） | `minSupportedVersion=0.1.12`（rollout 任意，强制优先） |

- 每次改 policy 都**新建 Release/tag**；不要依赖 `gh release upload --clobber` 后立刻验证（CDN 可能短暂返回旧值）。
- 临时 drill 测试后删除 Release/tag，恢复 `release/update-policy.json`，确认 latest stable 未被污染。
- 不要用快照版本号覆盖已发布 tag；临时演练建议单独 tag。

### 2.3 `update.json` 字段

```json
{
  "schema": 1,
  "versionName": "0.1.12-beta.1",
  "tagName": "v0.1.12-beta.1",
  "channel": "beta",
  "rolloutPercent": 100,
  "minSupportedVersion": "0.1.0",
  "publishedAt": "…",
  "htmlUrl": "https://github.com/.../releases/tag/v0.1.12-beta.1",
  "apk": { "name": "...", "size": 0, "sha256": "..." }
}
```

- `channel` 由 tag 是否含 `-` 决定；含 `-` 的 tag 在 Release workflow 中自动 `--prerelease`；
- 灰度比例与强制下限由 `release/update-policy.json` 生成，发布前提交 policy 改动。

### 2.4 发布后自检

```bash
gh release view vX.Y.Z --json isPrerelease,assets
gh release download vX.Y.Z --pattern '*-update.json' --dir /tmp/meta --clobber
cat /tmp/meta/*-update.json
curl -s https://api.github.com/repos/IAmKings/ZhiBox/releases/latest | jq .tag_name
```

确认：prerelease 标记正确、latest stable 未被 beta 顶替、资产与 SHA 完整。

## 3. 普通更新验收（P0，必过）

### O-01 首次启动自动检查
1. 设备 A 安装较旧稳定版（如 v0.1.9）；
2. 清除应用数据后首次启动（或卸载重装）；
3. **预期**：自动查询最新版本 → 按 DESIGN 弹窗展示版本/大小/日期/更新说明；
4. 记录：弹窗截图、`shared_prefs/app_update.xml` 时间戳（debug 包可 run-as）。

### O-02 24h 节流与自动检查开关
1. 关闭弹窗（稍后）→ 冷启动多次：24h 内不重复自动弹窗；
2. 设置 → 隐私与关于 → 更新设置：关闭「自动检查更新」→ 冷启动不联网、不弹缓存；
3. 手动「检查更新」仍可正常查询；
4. 重新打开开关。

### O-03 手动检查 + 取消/关闭
1. 设置 → 隐私与关于 → 检查更新；
2. 记录状态从「检查中」到结果；连续点击验证取消在途任务并重查；
3. Available 态：点「稍后」/外部空白/返回键均可关闭；
4. 再次手动检查可重新出现。

### O-04 前台下载 + 安装
1. 点「立即更新」→ 授权通知（首次）；
2. 观察进度百分比、大小、不可取消（返回键无效）；
3. 校验后拉起系统安装器 → 继续/安装 → 覆盖升级；
4. **预期**：安装后版本号 = 目标版本；应用数据保留；无签名错误；
5. **回归重点**：自更新完成、应用以新版本重启后**不得再弹「更新失败」**，关闭弹窗后才看到已更新属于 v0.1.12 已修复的 bug；再次检查更新应为「已是最新版本」。
6. **已验证（2026-10-28）**：v0.1.11 → v0.1.12 前台更新通过（无失败弹窗）。

### O-04b 离线/网络异常点击更新（v0.1.17-beta.2+）
1. 断网（飞行模式）后点「立即更新」；
2. **预期**：快速进入「更新失败（网络不可用）」，不应出现不可取消的「正在下载 0%」；
3. 若 WorkManager 长时间处于 ENQUEUED：20s 内自动失败，可重试/关闭；
4. 恢复网络重试可继续下载（`.part` 续传）。

### O-05 后台下载 + 通知
1. 开始下载后立即 Home/锁屏；
2. 通知栏出现「正在下载更新」进度；
3. 完成后通知「更新已下载 / 点击安装 X」；
4. 前台完成时自动拉起安装器；后台完成时点通知安装。

### O-06 进程被杀后续传
1. 下载中 `adb shell am force-stop com.zhibox.memory`；
2. 重新打开应用/等待 WorkManager 恢复；
3. **预期**：下载从 `.part` 续传而非从 0 开始（对比文件大小/进度），最终 SHA 校验通过；
4. 若网络受限，确认镜像回退后仍续传。

### O-07 未知来源权限
1. 系统关闭「安装未知应用」；
2. 完成下载后出现「需要安装权限」→「去设置」→ 授权 → 返回；
3. **预期**：返回后自动继续安装（无需重新下载）。

### O-08 失败与重试
1. 下载中开飞行模式/断网；
2. **预期**：可读错误（网络/超时/校验），弹窗可重试；恢复网络后重试成功；
3. 下载完成后 SHA 不符/签名不符：应拒绝安装并提示「安装包无效或签名不一致」。

### O-09 设置搜索/更新设置回归
1. 设置首页搜索「更新」「GPU」等，结果跳转正确；
2. 自动检查/Beta 开关持久化（重启后状态保持）。

## 4. Beta 通道验收（P0）

### B-01 stable 看不到 prerelease
1. 起始 v0.1.11，关闭 Beta；
2. 目标只有 prerelease（如 v0.1.12-beta.1）时，手动检查：显示「已是最新版本（当前）」或无更新；
3. GitHub `releases/latest` 不得返回 prerelease。

### B-02 开启 Beta 可见
1. 打开「接收预发布版本（Beta）」；
2. 手动检查 → 弹窗当前 → 目标 beta；
3. 可正常下载/安装（签名一致）；
4. 关闭 Beta 后再次检查：不再显示 beta。

### B-03 Beta → 正式版
当正式版 semver 高于 beta（如 0.1.12 > 0.1.12-beta.1）时，Beta 客户端应能收到正式版。

## 5. 灰度验收（P0，边界必过）

> 灰度分桶 = `sha256(installId|version)` 前 8 hex % 100；无法从 UI 看分桶值。
> **确定性的测试方式是 0% 与 100%**；10/50% 只做多设备抽样。

### G-01 rollout = 0（全部不命中）
1. 发布 `update.json rolloutPercent=0` 的 drill release（版本高于当前）；
2. 起始 v0.1.11 手动检查；
3. **预期**：设置行「新版本 X 正在分批推送（0%）」；**无弹窗**、不自动下载；
4. 多次检查结果一致；不写 dismissed（后续调整到 100 应能正常弹）。

### G-02 rollout = 100（全部命中）
1. 删除上一个 drill / 新建 rollout=100 的 release；
2. 手动检查 → 正常弹窗、可下载安装；
3. 记录从「分批推送」到「可更新」的变化。

### G-03 强制优先于灰度
`rolloutPercent=0` + `minSupportedVersion=目标版本` → 仍应弹强制更新（见 §6）。

### G-04 中间比例抽样（P1）
rollout=10/50，至少 5 台/5 个全新安装（不同 installId）手动检查：
- 记录命中/未命中数量；
- 未命中：只显示分批推送，不下载；
- 命中：正常弹窗；
- 不要求精确比例，但不得出现「未命中却弹窗下载」或「命中却永不提示」。

## 6. 强制更新验收（P0，仅可清空设备）

### F-01 强制弹窗
1. drill release policy：`minSupportedVersion=目标版本`（大于当前）；
2. 手动检查；
3. **预期**：标题「需要更新」+ 重要修复提示；**无「稍后」**；返回键/点外部不关闭；
4. 强制绕过分桶与「用户取消过的版本」。

### F-02 强制下载安装
1. 「立即更新」→ 前台/后台下载 → 校验 → 安装器；
2. 安装后版本 = 目标版本；再次检查显示最新。

### F-03 失败逃生
1. 断网/制造下载失败 3 次（每次重试）；
2. 第 3 次失败后出现「暂时退出」；
3. 点击可关闭；**再次启动仍会提示强制且不可取消**（缓存状态；v0.1.14 修复，旧版本会丢失 forced）；
4. 不得在未失败时出现退出入口。

### F-04 元数据异常
删除/破坏 `update.json` 或写非法 `minSupportedVersion`：
- 客户端应回退 100%/非强制（普通更新），不得误强制/锁死。

### F-05 恢复
- 测试后删除临时 Release/tag、恢复 policy；
- 清空应用数据/卸载重装，确认不再强制。

### G-05 灰度缓存刷新（P0，v0.1.17+）
1. 发布 rollout=0 的 drill Release（版本高于当前）；
2. 设备手动检查 → 显示「正在分批推送（0%）」，缓存该信息；
3. 将该 Release 的 `update.json` rollout 改为 100（或按 6h TTL 后再检查）；
4. 冷启动/手动检查 → 应能自动/手动重新检查到可更新，而不是永久停留在 pending；
5. 已命中设备在 rollout 调低后，TTL 到期应不再弹更新框。

## 7. 受限网络与镜像专项（P0 至少一台）

### N-01 APK 镜像回退
- 直连 GitHub 资产超时（如国内网络）→ 下载自动镜像回退，最终 SHA/签名通过。

### N-02 update.json 镜像回退
- v0.1.11 起始客户端：直连资产超时，灰度/强制元数据仍生效（K60U 已验证）；
- 对照：v0.1.10 及以前会回退默认值（记录预期限制，不作为缺陷）。

### N-03 线路诊断
高级与诊断 → 技术细节 →「更新线路」：显示直连/镜像状态；「重置线路状态」后重新检查。

## 8. 历史版本升级路径（P1，兼容性）

| 起始 → 目标 | 验证点 |
|---|---|
| v0.1.6 → latest stable | 旧客户端普通更新能发现/下载/安装；无 WorkManager 通知为预期 |
| v0.1.7/v0.1.8 → latest stable | 后台/通知/续传链路；元数据忽略为已知限制 |
| v0.1.9/v0.1.10 → latest stable | 通知被拒续装、cache-buster；灰度在直连可用时生效 |
| v0.1.11 → 内测 beta | 推荐基线：灰度/强制/后台/搜索全量 |

降级：卸载当前版本后安装旧版（数据清空）；不做同版本降级覆盖。

## 10. 内测发布操作顺序（推荐）

1. 代码冻结 → CI 全绿（docs/单测/lint/release 构建）；
2. 发布内测 prerelease（如 `v0.1.12-beta.1`，policy 100/0.1.0）；
3. 设备 A/B 安装历史版本（v0.1.9/v0.1.10/v0.1.11）→ 普通更新回归（O-01~O-09）；
4. 发布灰度 drill（rollout 0）→ G-01；再 rollout 100 → G-02；删除 drill；
5. 可清空设备 C 发布强制 drill（minSupported=目标）→ F-01/02/03；删除 drill；
6. 检查 latest stable 未被污染、policy 恢复；清理测试 Release/tag；
7. 发布内测公告；保留 v0.1.11 作为稳定回退；
8. 收集问题 → 修复 → 重复 1~7。

## 11. 常见坑（实战经验）

- **不要只覆盖同名 `update.json` 后立刻验证**：CDN 边缘可能返回旧值（v0.1.10 起有 cache-buster，但仍建议新建 Release/资产）。
- **beta tag 必须含 `-`**：否则会被当成正式版进入 `releases/latest`；release workflow 已强制 `--prerelease`。
- **灰度/强制测试基线必须 ≥v0.1.11**：更老客户端会忽略 `update.json`（v0.1.8 及以前）或在受限网络回退默认值（v0.1.9/10）。
- **厂商安装器差异**：MIUI/OPPO 可能多一步「未知来源」「风险确认」「继续安装」；测试步骤要预留。
- **通知被拒**：Android 13+ 拒绝通知后，后台完成无通知；回到应用前台会自动续装（v0.1.9+），需单独验证。
- **强制状态会缓存**：清理缓存/数据后才能恢复；不要在不可清空设备做强制演练。
- **force-stop 与后台切换不同**：force-stop 会取消 WorkManager，重新进入后恢复；普通 Home/锁屏应继续下载。
- **降级不覆盖**：versionCode 降低会被系统拒绝；历史版本测试先卸载。
- **自更新后误弹失败（v0.1.12 修复）**：若起始版本 ≤v0.1.11，自更新完成后可能弹
  「更新失败」而实际已升级；这是旧 WorkManager SUCCEEDED 被新进程重复消费导致，
  用 v0.1.12 起始版本回归；旧版本不修。
